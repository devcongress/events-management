# Volunteer selection decisions and outcome email delivery

Volunteer review status (`unreviewed`, `reviewed`, `needs_follow_up`) remains independent from the selection decision (`pending`, `accepted`, `not_selected`). Reviewers with `volunteers.review_applications` may save all three review fields together using an expected decision version. Saving never sends an email. The reviewer response contains only an outcome sent/not-sent indicator; campaign operations and detailed delivery diagnostics remain Owner-only.

The reviewer list uses the shared application pager and retains the ten-record page size while filters reset safely to the first page. Desktop rows align Applicant, Review, Invitation, and Submitted fields; phones keep search full-width and place the two equally wide filter controls beneath it, then stack the same labelled fields into full-row review buttons. The 40rem desktop review drawer keeps the full motivation and the complete Accra/19 December/no-travel-support question readable, with a cream/yellow availability answer and paired decision/status controls that stack on small screens. Review badges are shown only for submitted answers: invited applicants awaiting a response and applicants who were not invited have distinct neutral states, while invitation delivery remains a separate Sent/Not sent field.

The follow-up progress summary describes invitation delivery rather than volunteer selection: `Invitations pending` is limited to queued or sending invitations, `Responses received` means the follow-up form was submitted, and `Delivery issues` covers failed, bounced, suppressed, or complained invitations. These labels do not alter the underlying count rules.

## Saved outcome messages and Owner-controlled sends

Review-capability users maintain one accepted and one not-selected plain-text message above the review queue. Each save is append-only and compares the expected message version, so an older editor cannot replace a newer message. The versioned templates are service-role-only in the database; review and campaign APIs expose only decision, version, subject, and message. The Owner Campaign surface is intentionally read-only: it displays the saved copy and can request a preview, but cannot author browser-only text.

The Owner chooses Accepted or Not selected and requests a preview. The server rejects client subject/message fields, loads the saved template itself, and stores a ten-minute cohort snapshot containing eligible recipient IDs, decision versions, and the exact personalized escaped HTML/text payload to send. The preview shows production-rendered sample HTML/text, eligible/excluded counts, and the complete frozen recipient list (name, email, and decision version) in a keyboard-scrollable disclosure. The sample is labelled so it cannot be mistaken for every personalized message. Confirmation revalidates the complete eligible cohort and versions and queues only that snapshot in one transaction. A stale preview fails instead of expanding or silently replacing its audience. Reconfirming a completed preview does not enqueue duplicates. Pending decisions are never eligible.

After migration `20261018210000_volunteer_outcome_row_controls.sql`, confirmation creates one durable singleton Resend batch per recipient. Existing batches of up to 50 remain immutable and retain their original mapping. Every batch has one stable idempotency key, and each delivery retains its exact batch mapping and frozen payload. A claim obtains one whole batch atomically; a malformed, incomplete, duplicate, or ambiguous provider result retries the whole exact batch with that same key. Provider IDs are accepted only when their count equals the frozen batch count and every ID is unique, then mapped positionally to the frozen payload order. No individual recipient is retried from an ambiguous batch.

Outcome emails have separate pause/resume controls from the invitation campaign. The Owner workflow is explicit: save decisions in Reviews, choose Accepted applicants or Not-selected applicants, request a preview to establish authoritative eligibility, then confirm the frozen preview. Only the preview API supplies authoritative `eligible_count`; the delivery table never treats a missing provider ID as readiness to send. Confirmation is the only path that queues them; saving a decision or review does not. Enabling delivery only processes a confirmed queue. A decision cannot change after any outcome attempt, provider acceptance, or ambiguous send; same-decision note/status edits remain allowed and do not change the decision version. The collapsed Delivery health control is expressly provider-capacity and scheduler diagnostics, not a blanket delivery-health guarantee.

## Selected-volunteer broadcasts after acceptance

The Owner-only Campaign workspace opens on **Volunteer updates**, with separate **Outcome emails**, **Invitations**, and **Settings** tabs. Updates and outcomes load on their first visit and remain mounted, preserving draft copy, recipient selections, audience filters, and pagination when switching tabs. Wide screens place the update message beside recipient selection. Invitations keeps a compact progress summary above its applicant inbox; Settings contains the invitation deadline, preview/test links, queue controls, sending status, and delivery-health diagnostics. Delivery details remain shared across Invitations and Outcome emails. Desktop and mobile retain the existing Owner access checks and keyboard-operable tab navigation.

The Owner Campaign surface has a separate **Volunteer updates** composer for follow-up announcements such as orientation details. Its eligible pool is every recipient currently marked `accepted`, but nobody is selected automatically. The Owner may choose any subset, search or paginate without losing that selection, or explicitly choose all accepted volunteers.

Preview stores an actor-bound ten-minute snapshot of exactly the selected recipient IDs, decision versions, normalized addresses, and the rendered DevCon26 HTML/text. Confirmation revalidates only that frozen subset. A changed decision, version, or email rejects the confirmation; the server never expands the audience to newly accepted volunteers. The resulting history entry records the frozen recipient count and preparation status.

These updates use the programmatic Resend Segment and Broadcast workflow, not the transactional invitation/outcome batch sender. They share the same three reusable segment slots as event blasts: the queue clears prior contacts, imports the frozen audience in batches of ten, creates a Resend Broadcast draft from the frozen content, and then sends or schedules it. The segment remains reserved until reconciliation confirms a terminal provider state and cleanup verifies that no contacts remain. Immediate sends still respect the transactional capacity reserve. The existing accepted and not-selected outcome messages, controls, idempotency keys, and delivery rows are unchanged.

## Test an outcome email

The Owner campaign shows a **Try this email** box under the saved outcome message. Choose Accepted or Not-selected applicants, enter one address or use the signed-in email, and send a sample independently of audience eligibility. The server loads the saved copy and production template with the sample name Applicant and a `[TEST]` subject. This sends only to the chosen address and never changes applicant decisions, confirms a cohort, or adds campaign deliveries.

`POST /api/annual-conference/2026/volunteer-follow-up/outcomes/test` requires an Owner session, a strict decision/email/request-ID body, and the existing provider configuration. Omitted email defaults to the session identity. An Owner-scoped limit allows five requests per ten minutes. Retries retain a stable provider key independent of mutable saved copy; the UI retains its request ID on failure. Success means Resend acceptance, not inbox delivery. Test sends record provider quota health and a minimal admin audit best effort, without changing a successful response when reporting fails. Test sends do not appear in applicant delivery history.

## Outcome email presentation

Newly rendered outcome emails use straightforward headings, a small personal greeting, and escaped paragraph blocks without inset cards or side borders while retaining the saved subject and message. Accepted messages promote a standalone HTTPS Google Meet room link (optionally prefixed with “Join on Google Meet:” or “Video call link:”) into a simple button. Other URLs remain plain text. Non-selection emails include an Explore DevCon26 button and plain-text link to `https://devcongress.org/devcon26/`. A dedicated responsive letter shell uses a small logo, an unboxed reading column, and light/dark styling; other email templates retain their existing design. Existing frozen previews and queued payloads are not rewritten; the existing template-version label is unchanged.

## Delivery safety

Outcome history is durable and version-specific. Payload and provider sender fields are frozen with the preview and retried with one stable idempotency key. The outcome worker shares the invitation lease and transactional daily counter, so 54 is a combined daily claim maximum, not a per-stream allowance; both streams respect the 35-message reserve and require complete, fresh quota observations. Pre-send quota observations come from Resend's read-only usage endpoint and accept only non-negative safe-integer daily/monthly `used` values; plan limit fields are not used for this guard. Claims validate the lease, current decision/version, and claim token before provider calls and again on finalization. The batch-wide pre-send validation and post-send webhook replay each use one database request, including for legacy multi-recipient batches, to stay inside the Worker's outbound-request budget. A verification error before provider contact finalizes the claim for retry or Owner attention. Expired `sending` claims are included in drain discovery; inside the safe provider window they can be reclaimed with the same key, while claims past the 23-hour bound move to Owner attention. Webhook events are journaled/replayed against the durable delivery record. Migration `20261019080000_volunteer_outcome_batch_validation.sql` must be applied before the Worker change.

Definite provider rate limits and transient failures use bounded backoff with the same key. Network errors, malformed successful provider responses, and server errors are treated as ambiguous: the attempted decision remains locked, and the same payload/key may be retried only within the provider's safe window and attempt limit. Otherwise the Owner sees needs-attention diagnostics. The campaign diagnostics list is scrollable and does not silently truncate later recipients. No automatic opposite-outcome email or conflict resolution is introduced.

## Failed-delivery retry and diagnostics

Owners can queue—not send—one failed invitation or outcome again only when Resend definitely rejected it before acceptance, it has no provider ID or webhook event, has no live claim or scheduled automatic retry, is below four attempts, and remains inside the original 23-hour idempotency window. Invitation retries also require an unsubmitted, deadline-eligible application inside the 14-day response window; outcome retries require the current decision/version and the frozen payload. The atomic database operation keeps the original payload, idempotency key, attempt count, and first-attempt timestamp; repeated or concurrent clicks queue no duplicate work.

Provider HTTP status, failure certainty, stage, and timestamp are stored separately from a sanitized message. Owner diagnostics distinguish EMS request/account checks, provider rejection, uncertain result, and provider event without claiming a bounce proves the root cause. Accepted, delivered, bounced, complained, suppressed, historical, and ambiguous records are never manually resent. Invitation pause state and outcome pause state remain independent: a queue action while its own queue is paused waits for a separate Owner resume and never changes campaign controls.

The Owner campaign view shows a safe contextual sender status beside progress and controls. It maps only recognized invitation/outcome drain results, always shows the recorded scheduler timestamp when available, gives Draft/Paused/Closed state precedence, and marks older or non-running results as historical. Raw provider or arbitrary scheduler strings never reach the UI. An accepted provider batch remains accepted even when its post-send response lacks quota headers; the next pre-send usage read controls whether additional work can start.

The scheduled worker gives this queue four isolated processing opportunities in each 15-minute cycle (slots 0, 9, 11, and 13). One invocation processes at most one invitation or outcome queue item, retaining the existing lease, capacity, retry, and idempotency rules. These are processing ceilings, not four guaranteed invitations, and they are intentionally not evenly spaced: the first opportunity is followed by a nine-minute gap, then two-minute gaps. When outcomes are due while invitations are running, deterministic 15-minute wall-clock windows alternate invitation and outcome priority, producing four invitation turns and four outcome turns across 30 minutes when work remains eligible; the 54/day campaign limit still applies. Pre-send failures record and emit only a safe drain stage plus `resource_limit` or `internal` category, never provider payloads, database messages, links, or recipient details.

## Per-email delivery table and controls

The Owner campaign includes an always-visible delivery table below Queue delivery, separate from Delivery health. It scopes rows to the selected acceptance or not-selected audience, searches names/email addresses, filters All / Needs attention / On hold / In progress / Delivered / Not queued, and paginates ten rows at a time. Phones stack labelled row content without horizontal scrolling. Provider acceptance is not labelled Delivered. Previous-decision records and unknown states call for review instead of suggesting success. Details explain attempts, next eligible retry time, recorded errors, and recovery restrictions; the parent refreshes every minute.

New individual deliveries can be held or resumed through Owner-only `POST /api/annual-conference/2026/volunteer-follow-up/outcomes/delivery-control` with `delivery_id` and `action` (`hold` or `resume`). The server selects the campaign and actor, rate limits changes, and calls a service-role-only transaction sharing the sender's campaign lock. Holding prevents future claims; it cannot recall a request already sending. Resume clears only hold metadata: frozen payload, provider key, attempt history and retry schedule remain unchanged. Global queue pause still wins. Four attempts, the 23-hour provider idempotency boundary, changed decisions, provider acceptance and uncertain terminal results prevent unsafe resumes. Eligible definite failures use the existing retry confirmation action; held records cannot bypass the hold via that endpoint.

Legacy rows explicitly lack individual controls, even if their old batch contains only one recipient. They retain the existing queue-wide pause and guarded batch retry through delivery review. No old batch is split or re-keyed. The scheduler still claims one batch per outcome turn: singleton sends reduce throughput (approximately eight recipients/hour while the existing alternating invitation/outcome schedule is active), with the same shared 54-recipient daily cap and provider-capacity reserve. No capacity limits are raised.

Apply the new migration before deploying these API/UI changes. Local validation: `node scripts/test-volunteer-outcome-row-controls.mjs` starts and destroys an isolated socket-only PostgreSQL cluster, covering singleton confirmation, legacy preservation, holds, resumes, retries, expiry, global pause, claim races and SQL role boundaries. It does not connect to production. The offline migration gate checks inventory/contracts only; release still requires the live migration gate.
