# Telegram ticket purchase notifications

DevCon26 live Paystack orders can queue private Telegram notifications for confirmed payment, incomplete checkout, required refunds, completed refunds and refunds needing attention. Incomplete checkout means a terminal failed, abandoned or reversed observation, or expiry of an unpaid checkout hold; pending or ongoing checkout does not notify. A terminal observation and expiry share one deduplication key. Partial seat refunds notify separately; the final order status change does not create another refund alert. Test and complimentary orders are excluded. Each message links to the protected Ticketing Orders list and excludes purchaser details, payment references and admission capabilities. Existing events are not backfilled.

Payment-success messages snapshot paid live Paystack seats so far, less completed partial seat refunds for orders still paid. The count reflects the ledger visible to the payment transaction; a refund completing concurrently may not yet be visible in that snapshot.

Delivery is disabled unless `DEVCON26_TELEGRAM_PURCHASE_NOTIFICATIONS_ENABLED=true`, `DEVCON26_TELEGRAM_BOT_TOKEN`, `DEVCON26_TELEGRAM_CHAT_ID` and an ISO 8601 timestamp with timezone in `DEVCON26_TELEGRAM_PURCHASE_NOTIFICATIONS_START_AT` are configured. Events occurring before that timestamp, including expired holds, are suppressed. Configure secrets outside the repository and verify the destination's audience before enabling. The canonical Worker retries every five minutes independently of payment fulfillment; provider delivery failures do not affect checkout. Enqueue is atomic with the originating transition when it succeeds. If the outbox insert fails, the trigger emits a generic database warning and allows fulfillment to continue; that alert is lost and is not backfilled automatically.

Telegram has no idempotency key. A definite 429 with a valid retry delay is retried at most five times; a timeout, network error, invalid response or other provider failure after a request starts is parked for manual review to avoid duplicate sends. A stale lease is reclaimed only before its request starts. Provider acceptance is not proof of recipient reading. Apply and verify the migration before enabling the Worker; do not send historical alerts by setting the start timestamp in the past.

For a `needs_review` row, an authorized operator should check the private Telegram chat and reconcile the pass, seat count, amounts and time without copying purchaser information. If the message is present, mark the row sent through a reviewed service-only database operation. If it is absent, a deliberate requeue may still duplicate a message whose provider outcome is uncertain; record that decision and clear the request-start marker only as part of the reviewed operation. Never blindly requeue the whole review backlog.
